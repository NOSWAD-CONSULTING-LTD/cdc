# Reference Architecture for CDC Manufacturing Ontology

This ontology is the semantic contract for the CDC Neo4j demo. It defines what the graph concepts mean, which relationships are allowed, and which constraints should hold for a well-formed graph.

The ontology sits above the Neo4j instance model:

```text
Ontology = classes, properties, meanings, constraints, vocabularies
Neo4j graph = actual product, recipe, run, CDE, evidence, and relationship instances
```

This is a reference ontology for architecture discussion. It is not a validated GxP ontology and does not replace formal quality-approved data standards.

## Namespace

The ontology examples use this namespace:

```text
https://example.com/ontology/cdc#
```

The namespace is intentionally fictional for demo use.

## Class Groups

### Product Domain

| Class | Meaning |
| --- | --- |
| `Product` | Medicinal product being manufactured and controlled. |
| `Formulation` | Versioned product composition. |
| `Material` | Material master record for API, excipient, lubricant, or coating material. |
| `MaterialLot` | Physical lot of material used in manufacturing. |
| `Supplier` | Qualified source of a material or lot. |
| `IntermediateProduct` | Material state produced between unit operations. |

### Process Domain

| Class | Meaning |
| --- | --- |
| `Recipe` | Versioned manufacturing recipe. |
| `ProcessStep` | Step inside a recipe. |
| `ProcessSegment` | High-level stage of the end-to-end manufacturing flow. |
| `UnitOperation` | Conceptual process stage from crystallisation to coated tablet collection. |
| `MaterialTransformation` | Material state change across a unit operation. |
| `ControlPoint` | Point where process monitoring or control is applied. |
| `SamplingPoint` | Location or event where data or material sample is collected. |

### Asset Domain

| Class | Meaning |
| --- | --- |
| `ManufacturingSite` | Facility where manufacturing is performed. |
| `ManufacturingLine` | Integrated manufacturing line. |
| `Room` | Controlled manufacturing area. |
| `Equipment` | Physical asset used by a process step or unit operation. |
| `Sensor` | Instrument, historian tag, PAT model, or soft sensor. |
| `DataSourceSystem` | System of record or source system for a CDE. |

### Quality Domain

| Class | Meaning |
| --- | --- |
| `CPP` | Critical Process Parameter. |
| `CQA` | Critical Quality Attribute. |
| `CriticalMaterialAttribute` | Material attribute that can affect process performance or product quality. |
| `Specification` | Acceptance criterion or limit. |
| `SensorReading` | Time-stamped process or quality value. |
| `AnalyticalMethod` | Method used to measure a quality attribute. |
| `AnalyticalResult` | Result generated by an analytical method. |
| `Alarm` | System event triggered by a reading or process condition. |
| `Deviation` | Quality investigation for an unexpected event or excursion. |
| `QAReleaseDecision` | QA disposition decision for a run or batch. |

### Manufacturing Execution Domain

| Class | Meaning |
| --- | --- |
| `ManufacturingRun` | Executed manufacturing event using recipe, materials, assets, and records. |
| `BatchRecord` | Electronic batch record summary and review evidence. |
| `CleaningRecord` | Cleaning or line-clearance evidence. |
| `CalibrationRecord` | Instrument/equipment calibration evidence. |
| `Operator` | Person participating in execution or review. |

### Governance Domain

| Class | Meaning |
| --- | --- |
| `CMCPackage` | Chemistry, Manufacturing, and Controls knowledge package. |
| `RegulatoryFiling` | Filing or regulatory evidence package. |
| `RegulatorySection` | CTD Module 3 / CMC section. |
| `ValidationEvidence` | Validation or evidence artifact. |
| `EvidenceDocument` | Demo document-style evidence supporting CDE values, mappings, batch records, QA decisions, or filing context. |
| `ProcessValidation` | Validation package connecting process, recipe, and run evidence. |
| `ControlStrategy` | Integrated control strategy protecting CQAs. |
| `RiskAssessment` | Risk assessment connecting CMAs, CPPs, CQAs, and controls. |
| `ChangeControl` | Governed change assessment and approval. |
| `SOP` | Standard Operating Procedure. |
| `TrainingRecord` | Training evidence for an SOP or process. |
| `EquipmentQualification` | Qualification evidence for equipment. |
| `ComputerSystemValidation` | Validation evidence for computerized systems. |
| `AuditTrailEvent` | Data integrity evidence for an event or decision. |

### Data Governance Domain

| Class | Meaning |
| --- | --- |
| `CriticalDataElement` | Governed metadata record for a critical data element. |
| `DataStandard` | ICH, ISO, ISA, or CTD standard/guidance context. |
| `StandardMapping` | Explicit mapping between a CDE, standard, and regulatory section. |
| `DataQualityRule` | Rule used to assess required CDE quality. |
| `DataOwner` | Business owner accountable for the CDE. |
| `DataSteward` | Steward responsible for CDE definition and quality. |
| `ValueDomain` | Data type, unit, and allowed-value context for a CDE. |
| `UnitOfMeasure` | Controlled unit used by a value domain. |
| `AllowedValue` | Permissible categorical value for a value domain. |
| `CDEVersion` | Versioned CDE definition. |
| `CDEDefinitionApproval` | Approval record for a CDE definition version. |
| `CDEValue` | Representative observed or textual value for a CDE. |
| `ProvenanceStatement` | Citation and source context supporting a standard or mapping. |
| `CDEDomain` | Controlled vocabulary node classifying CDE domain. |
| `CriticalityLevel` | Controlled vocabulary node classifying CDE criticality. |
| `DecisionStatus` | Controlled vocabulary node classifying QA decision/disposition values. |
| `RunStatus` | Controlled vocabulary node classifying manufacturing run status. |
| `DeviationSeverity` | Controlled vocabulary node classifying deviation severity. |
| `RelationshipDefinition` | Machine-readable Neo4j relationship and ontology predicate alignment record. |

## Core Semantic Patterns

### Product And Recipe

```text
Product hasFormulation Formulation
Product hasRecipe Recipe
Product hasCMCPackage CMCPackage
Formulation usesMaterial Material
Recipe definesStep ProcessStep
```

### End-To-End Process

```text
ProcessSegment containsOperation UnitOperation
UnitOperation nextOperation UnitOperation
UnitOperation produces IntermediateProduct
UnitOperation hasTransformation MaterialTransformation
UnitOperation hasControlPoint ControlPoint
UnitOperation hasSamplingPoint SamplingPoint
```

### Materials And Genealogy

```text
MaterialLot instanceOf Material
MaterialLot suppliedBy Supplier
ManufacturingRun consumes MaterialLot
ManufacturingRun produces IntermediateProduct
```

### Assets And Sensors

```text
ManufacturingSite hasLine ManufacturingLine
ManufacturingLine hasRoom Room
ManufacturingLine includesEquipment Equipment
Equipment locatedIn Room
Equipment hasSensor Sensor
Sensor measures CPP
Sensor measures CQA
SensorReading recordedBy Sensor
SensorReading duringRun ManufacturingRun
```

### Quality And Control

```text
CPP controls ProcessStep
CPP impacts CQA
CQA hasSpecification Specification
CriticalMaterialAttribute characterizes Material

ControlStrategy protects CQA
ControlStrategy usesCDE CriticalDataElement
```

### Quality Events And Disposition

## Ontology Rules

Recommended semantic rules:

- Every `Product` should have at least one `Formulation`.
- Every `Product` should have at least one `Recipe`.
- Every `ManufacturingRun` must execute exactly one `Recipe`.
- Every `ManufacturingRun` should have one `BatchRecord`.
- Every released `ManufacturingRun` should be released by a `QAReleaseDecision`.
- Every rejected `ManufacturingRun` should be rejected by a `QAReleaseDecision`.
- Every `MaterialLot` must be an instance of one `Material`.
- Every `MaterialLot` should be supplied by one `Supplier`.
- Every `SensorReading` must be recorded by one `Sensor`.
- Every `SensorReading` must occur during one `ManufacturingRun`.
- Every `CQA` should have at least one `Specification`.
- Every `CriticalDataElement` must be observed at one or more `UnitOperation` nodes.
- Every `CriticalDataElement` must have a source system, owner, steward, data quality rule, value domain, definition version, approval, representative value, and standard mapping.
- Every `CriticalDataElement` that supports regulatory evidence should map to a `RegulatorySection`.
- Every `CDEValue` should reference exactly one `CriticalDataElement`, one `ValueDomain`, and one `ManufacturingRun`.
- Every `StandardMapping` should be supported by one or more `ProvenanceStatement` nodes.
- Every `EvidenceDocument` should connect to at least one graph evidence target.
- Every `CriticalDataElement` should connect to controlled vocabulary nodes for domain and criticality.
- Every `RelationshipDefinition` should define a Neo4j type, ontology predicate, subject label, and object label.
